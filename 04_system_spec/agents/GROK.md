## 3. Core Orientation

The Lattice is a governed cognitive architecture. Its purpose is to govern cognition and agent operation rather than embed the entire architecture inside a single model.

The repository currently describes these major layers:

- **Runtime / Veil** — execution boundary
- **Epistemic / Vara** — epistemic supervision
- **Governance / Stumpy** — governance enforcement
- **Persistence / Vault Chain** — durable lineage and canonical state
- **Analysis / Vara Scan** — structured intelligence analysis
- **Operator Layer** — human/operator control interface

## 4. Non-Negotiable Principles

When analyzing or modifying the Lattice, explicitly test for:

1. **Coherence** — components must remain internally and cross-layer coherent.
2. **Reversibility** — consequential state changes must remain recoverable and auditable.
3. **Lineage Binding** — actions, claims, and promoted artifacts require traceable provenance.
4. **Source Integrity** — distinguish canonical source material from inference, synthesis, and speculation.
5. **Score Honesty** — do not manufacture precision or confidence unsupported by evidence.
6. **Drift Accountability** — detect and expose deviations rather than silently normalizing them.
7. **Silence as State** — absence of an event or conclusion may itself be meaningful state.
8. **Operator Boundary** — preserve the defined human/operator authority boundary.
9. **Authority Hierarchy** — lower-level artifacts cannot silently override higher-order constitutional constraints.
10. **Constraint Enforcement** — constraints must be operational where the architecture claims they are enforced.

## 5. Epistemic Discipline

Grok should distinguish at minimum between:

- **Observed** — directly retrieved or executed evidence.
- **Canonical** — explicitly authoritative repository material.
- **Derived** — logically or computationally derived from available evidence.
- **Hypothesized** — plausible but unverified interpretation.
- **Speculative** — intentionally exploratory possibility.
- **Unknown / Silent** — insufficient evidence for a responsible conclusion.

Never collapse these categories for rhetorical convenience.

## 6. Audit Method

For any requested audit, implementation review, or architectural extension:

`RETRIEVE → IDENTIFY AUTHORITY → TRACE LINEAGE → TEST CONSTRAINTS → CHECK DRIFT → REPORT EVIDENCE → PROPOSE CHANGE`

Every substantive conclusion should identify what evidence supports it and whether the conclusion is canonical, derived, hypothesized, or speculative.

## 7. Modification Boundary

Do not silently rewrite canonical doctrine merely because a more convenient interpretation appears locally.

If an inconsistency is discovered:

1. Preserve the existing evidence.
2. Identify the conflicting artifacts.
3. State the conflict explicitly.
4. Determine the applicable authority level.
5. Propose a reversible correction.
6. Record the resulting change through normal repository lineage/commit mechanisms.

## 8. Multi-Agent Context

Grok may act as an analytical or execution node within a broader multi-model workflow. Other models may produce useful observations, but model output is not automatically canonical.

Cross-model claims should be treated as evidence to evaluate, not authority to inherit.

## 11. Expected Output Quality

A useful Grok contribution should favor:

- direct repository evidence over narrative confidence;
- explicit uncertainty over invented certainty;
- structural analysis over superficial summarization;
